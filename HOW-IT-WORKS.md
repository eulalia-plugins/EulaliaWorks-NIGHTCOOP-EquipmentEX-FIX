The fix has two connected paths: an ordinary gameplay outfit path in the patched NightCoop runtime, and a photo-actor reconciliation path in REDscript and CET. They solve different problems. The native bridge makes the sender report the outfit it actually configured. The SDK photo bridge tells the receiver which extra slot each received clothing record belongs in. Neither path transfers meshes or textures to another PC.

Equipment-EX stores a logical outfit in OutfitSystem's state. A configured OutfitPart can exist even when its visual ItemObject is absent or changing because of the current camera or player representation. Reading only TransactionSystem.GetItemInSlot therefore is not always equivalent to asking what the player is wearing. If a synchronization snapshot treats a camera-dependent absence as an unequipped item, peers can receive changing or incomplete clothing state even when they installed identical mods.

The added OutfitSystem.NightCoopReadConfiguredItem(slotID) reads m_state.GetPart(slotID).GetItemID() while the outfit state is active. It is a read-only access path: it does not equip items, spawn visuals or change the outfit. GameObject.NightCoopReadOutfitSlot first proves that the object is the local main player. For that actor, active Equipment-EX outfits and OutfitSlots use the configured-state getter. Other actors and ordinary slots retain a transaction-system lookup and ItemID.None when no item exists. The native sender calls this separate method instead of repurposing a shared GetItemID function pointer used elsewhere.

An item record ID identifies a definition, not necessarily the complete item instance. The native bridge therefore keeps the complete 16-byte ItemID rather than converting the result back into a record-only identity and reconstructing it. The replacement reader zero-initializes its full output, checks nullable handles and runtime lookups, resolves gameObject and the added method, and invokes the script engine using the original object as receiver. Caller scratch buffers and diagnostics were adjusted to read the same complete result. The existing prologue, nonvolatile register handling, unwind data and surrounding cache mutex lifetime were preserved.

The R2 port correction matters here. The 0.2.0 function resolver used by this path compares CBaseFunction.shortName, not the mangled fullName. Looking up NightCoopReadOutfitSlot;TweakDBID through that resolver returned no method and produced empty outfit snapshots. The corrected patch resolves NightCoopReadOutfitSlot and calls the direct generic script invocation routine with the right argument contract. A test that executed the actual resolver reproduced the full-name failure and confirmed the short-name success; a mock resolver had missed it.

Placement is a second issue, independent of identity. EEX can append its intended slot to a clothing record's placementSlots and update mappings when a user moves an item. Taking placementSlots[0] can collapse different extra items onto a generic slot. The native selector preserves the original first-slot fallback, examines the final placement slot, and uses it only if it matches one of the 54 OutfitSlots recognized by this NightCoop build. It does not search arbitrary unknown extra slots or turn the 54 names into unlimited support. The helper uses existing name and CRC tables, volatile registers and image-relative references, with no additional stack frame. The PE text virtual size covers the helper placed in existing raw padding. Unwind metadata remains unchanged.

The vehicle component is a separate local appearance refresh. PlayerPuppet wrappers call the original mounting, unmounting and driver-camera methods. For the local player, a vehicle mount schedules refreshes at 0.1 and 0.5 seconds, an unmount at 0.1 seconds, and a switch into the driver's third-person camera at 0.35 and 0.8 seconds. The delays cover attachment updates occurring across separate ticks. The callback checks the outfit is still available and active, then detaches and reattaches its current visuals. It does not broadcast another player's saved outfit or change their inventory. It is not, by itself, a universal photo-mode attachment fix.

Photo mode creates another representation of a player. A correct gameplay body does not prove that the remote photo double has inherited every extra slot, clothing visual or simulation behavior. The extra-slot registration tweak explicitly extends the female and male TPP cutscene character records with OutfitConfig.OutfitSlots, avoiding duplicates, so NightCoop's runtime clones inherit the slot list even when EEX's ordinary template/display-name heuristics skip them. Registration alone does not prove an attachment has spawned.

Remote-photo identity is checked before mutation. The actor must be an NPCPuppet, must not be the viewer's local photo puppet or the ordinary Character.Player_Puppet_Photomode record, must use one of the two exact base photo templates, and must contain a PhotoModePlayerEntityComponent. This deliberately excludes the normal local gameplay actor and the viewer's own photo double. It is a specific filter for this implementation, not a blanket claim that any NPC is a partner.

EEX normally equips a preview/photo puppet using the viewer's OutfitSystem. Applying that behavior to a peer-owned double can put the viewer's outfit on the other actor or interfere with NightCoop's received outfit. The modified SetupInventory wrapper still calls the original method, then skips EEX's local-outfit application for recognized received photo actors. Its OnItemAddedToSlot wrapper likewise delegates those actors to the original path. Local photo behavior keeps the normal EEX path. SDK HookDeclare records the relevant wrappers; declaration does not itself replace their bodies.

For precise photo placement, GameObject.NightCoopPhotoConfiguredSlots reads only the local player's active EEX configuration and returns alternating slot and clothing-record TweakDBIDs. This is intentionally a slot-to-record map, not another serialization of the full gameplay ItemID. The native outfit stream supplies received inventory; the supplemental map supplies the exact target slot. For example, a record assigned to OutfitSlots.EarRight is not guessed from a generic mask slot or from whichever placement happens to be first on the receiving PC.

The CET module registers eulaliaworks.eex_photo, protocol 1, with NeededByAll and UsesChannels (257). The separate eulaliaworks.eex_bridge registration declares the EEX/vehicle/photo hooks. Participants need matching addon files. The sender transmits reliable slot-map messages on channel 1 to the SDK's other-peer destination, on changes and on a five-second heartbeat. It polls at approximately 0.25-second intervals and processes at most 32 queued SDK events per pass. Its scheduler combines nonnegative frame delta with wall-clock elapsed time, so a zero simulation delta during freeze does not stop communication.

The wire format begins NCP5| followed by slotHash,slotLength:itemHash,itemLength; pairs. Hashes are unsigned decimal integers; lengths are bounded to 1..255. Using hash plus length avoids depending on a printable TweakDB debug name being registered on the receiver. The decoder rejects the wrong prefix, malformed/trailing data, payloads over 4096 characters, more than 54 pairs, invalid numeric ranges, duplicate slots and duplicate item records. One record worn twice in different slots is therefore a current limitation. Invalid updates leave the last valid map intact. Non-message SDK events are not mistaken for payloads. Version 5.1 uses typed PollEvent fields rather than an assumed text-event layout; logs verified that valid maps actually arrive.

Matching an incoming map to a photo actor is conservative but not perfect identity binding. The receiver considers current peers in the same world, waits until it has a map for every candidate, and scores each map by how many record IDs exist in that actor's received inventory. With one candidate it selects that peer. With multiple candidates it requires a unique best score, a nonempty map and at least 75 percent matching items. Ambiguous results are skipped. Two people with identical outfits can therefore be ambiguous; this should eventually be replaced with an authoritative SDK actor-to-peer association.

NightCoopPhotoApplySlots validates the entire mapping before attachment writes. The target must be a recognized remote photo actor; the map must have an even number of values and fit the 54-pair limit; every slot must belong to the installed EEX slot list; records must be unique clothing records; and each original record must exist in the actor's received inventory. Missing received items cause a waiting result rather than silently copying the viewer's inventory. After validation, a first pass removes mapped items from incorrect extra slots so swaps do not evict each other. A second pass retains correct items, submits attachments to empty intended slots and reports conflicts or failures. Known completed attachments are refreshed once per item identity, not rebuilt on every update.

Hair under world freeze is addressed through an actor-level clock exception. The code does not selectively unfreeze individual hair bones. For a recognized remote photo double it calls SetIndividualTimeDilation with reason NCoopPhotoHairClockV5, scale 1.0, indefinite duration, and the ignore-global/local flags used by this implementation. This allows that actor's simulation and secondary motion to progress while global world dilation stays frozen. NightCoop's native photo system supplies the received pose/clip time and turns off the double's move components; these are existing native behaviors, not new bone-pose packets invented by the Lua addon. The user confirmed hair and posing working in the tested setup. Release/detach, session exit and shutdown paths unset the named individual override. The code does not globally resume the world to fix hair.

R3 addresses a distinct crash, not a clothing or physics problem. A captured partner dump faulted in the stock 0.2.0 pose-record CRC loop while hashing a modded pose name containing a curly apostrophe. The loop sign-extended UTF-8 byte 0xE2, producing an invalid CRC lookup-table index such as 0xFFFFFF33. The patch changes the one affected load from MOVSX to MOVZX (41 0F BE 09 to 41 0F B6 09 at RVA 0xBB2333, file offset 0xBB1735). Byte values stay in 0..255. Exactly one byte differs from the working R2 DLL. The actual native CRC loop matched standard CRC32 in 515 cases, including the captured pose name and non-ASCII inputs. This is not a general rewrite of signed-byte instructions throughout the DLL.

The latest facial-accessory branch remains experimental. Earlier logs showed the original raid_psy_visor4_accessories_silver accepted into an attachment request but remaining pending. Asset inspection found explicit Female/TPP and Male/TPP appearances. Version 5.3 cloned the record into separate photo-only female/male records with explicit appearances and empty suffix lists, leaving the original wearable's flats alone. Its live log then showed the clone attachment rejected, and its up-front removal of the original made the failure destructive. A separate flaw constructed the request and preview identities independently.

Version 5.4 persists one request-derived preview ID, grants using that same request, verifies that exact preview identity exists in the photo actor inventory, and equips the ID returned by that data. It avoids deleting the original in advance. An original occupying the intended target is submitted through the transaction system's in-place replacement path; originals in other slots are cleaned up only after the clone reports IsVisualSpawnAttached. This is not a guarantee of visual atomicity inside the engine. The copy is removed from photo slots when the source no longer wears it. A completed copy later evicted by an appearance rebuild can become eligible for a new submission. Only this exact silver accessory uses the special branch; it does not claim to fix all face items. The original camera-suffix hypothesis and final rendering result remain unproven.

The reports distinguish successful API submission, inventory presence, a populated attachment slot and a visually attached mesh. These are different milestones. A true AddItemToSlot return is not proof that a visible garment rendered; compilation is not a co-op visual test. Existing rejection evidence for a neck item and two belts is separate from the spider accessory and should not be reported as three facial-cyberware failures.

The package is deliberately version-pinned. apply_native_patch.py reads an existing official DLL, requires its exact SHA256, verifies each original patch range and bounds, rejects overlapping ranges, and requires the final R3 SHA256 before writing a new file. It does not discover the game, download anything, install itself, access processes or change security settings. The source bundle omits the runtime DLL, SDK definitions and private logs. The separate current-runtime ZIP is a convenient installed-file snapshot and explicitly includes the modified core DLL. Neither package silently replaces switches.txt; merge the three documented photo settings. Keep NightCoop and EEX's normal dependencies installed and preserve their license notices.

The native reader/resolver harness covers 700 cases and full 16-byte results with canaries, nullable paths and an unchanged receiver object. The selector harness covers 109 cases across the build's 54 recognized names and fallback behavior. The LuaJIT tests exercise the actual controller with typed SDK events, 21 protocol cases, zero-delta scheduling, malformed update preservation, own-photo exclusion, ambiguous-peer handling and clock cleanup. The latest REDS compiles against all installed scripts and new SDK definitions. These checks provide narrow, reproducible evidence; they do not certify every outfit, animation, gender combination, player count or third-party mod. SmartFrames synchronization is not implemented by this release.
